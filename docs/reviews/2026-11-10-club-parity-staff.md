# 구단 간 기록 동등성: 감독·코치·스카우트·분석원

기록은 구단의 실제 명단 변경과 계약 확정 시점에 `staffHistory(kind, person, action, tid, detail)`를 호출해 남긴다. 이 공통 함수는 명시한 구단 ID로 `chron('mgr'/'coach'/'scout'/'analyst', 이름·보직·원인·조건, null, tid)`를 호출한다. 선수 ID로 오해할 수 있는 직원 ID를 선수 링크에 넣지 않는다. 소식 기사, 시장 후보 배열, 현재 직원 명단이 없어져도 연대기의 인물 이름과 사건은 남는다.

수정 경로:

- `staff/30_manager.js`, `staff/73_firings.js`: 실제 감독 선임, 성적에 따른 경질·자진 사퇴, 대행 선임·임무 종료·정식 감독 승격. 정식 감독이 대행을 대체하는 경우 대행 경질로 기록하지 않는다. 신임 사단의 기존 코치 교체·합류도 각 구단에 기록한다.
- `staff/24_coaches.js`: 직접 채용·해임·연장, 보직 승격·맞교환, 감독 사단 합류·동반 퇴임, 계약 만료·재계약·후임 채용, 현 구단과 전 구단의 보조 코치 만료·정원 축소.
- `staff/89_coach_market.js`: AI 월간 시장 영입과 기존 코치 교체, AI 사이 승격 이적과 원 구단 후임 선임, 영입 제안의 실제 수락과 잔류 계약. 이적 기록은 원 보직을, 영입 기록은 새 보직을 사용한다.
- `staff/40_analysts.js`, `staff/51_staff_league.js`: 분석원 직접 채용·정리, 사용자 경쟁 영입 확정, AI 시장 영입·교체, 스카우트·분석원 양 구단 이적, 경쟁 제안 만료 후 실제 계약, 은퇴. 낮은 능력이라 리그 소식 기사가 없는 인사도 연대기에 남긴다. `stJoin`의 실제 영입 기록은 경쟁 메일이나 `wire`에서 다시 추가하지 않는다.
- `staff/73_firings.js`: 야인 기간 전 구단의 후임 단장 스카우트·분석원 충원도 원 구단에 기록한다.
- 총괄에게 추가 허용받은 `development/31_dev_medical.js`의 `scoutFire`, `contracts/09_stoveleague.js`의 사용자 감독 최종 계약 종료에도 같은 후크를 적용했다. 총괄 요청에 따라 같은 파일의 사용자 FA·트레이드 요약 연대기는 공통 실제 선수 이동 기록과 중복되지 않도록 제거했다.

연간 감독 재계약·계약 만료는 `career/32_people.js` 담당자와, 다른 구단 코치를 직접 빼오는 `contracts/38_poach_fagrade.js` 및 OB 스카우트 직접 채용 UI는 총괄과 연결했다. 명시 구단 기록의 영속 보관·타 구단 `gm=0` 판정·타 구단 조회 화면은 총괄의 공통 연대기 변경을 따른다. 과거 세이브에서 이미 사라진 직원 인사 내역을 추정해 복구하지 않는다.

계약 확정 이전의 후보 조회·경쟁 제안에는 선임 기록을 추가하지 않는다. 기존 인사 결정, 연봉, 보상금, 선수 소속과 의사결정 권한은 변경하지 않았다. `coachYear`는 기존 결정 순서를 유지하면서 만료·재계약·대체 채용 결과를 구분해 기록하도록 정리했다.

검증: `node tools/check-club-staff-history.cjs`

메모리 `build({write:false})` 엔진으로 **17개 통과**. AI 감독 경질·후임 각 1회, 대행 정식 승격·임무 종료 구분, 사용자 감독 교체, 코치 직접 인사·연장·AI 만료/재계약·월간 영입, 양 구단 이적과 밀려난 직원, 경쟁 제안과 실제 확정 시점, 스카우트·분석원 월간 AI 채용·이적·은퇴, 야인 전 구단 충원, 전 구단 보조 코치 만료, 직접 직원 해임, 시장·뉴스 삭제 후 JSON 저장 복원의 기록 보존을 확인한다. 배포 번들·커밋·푸시는 생성하지 않았다.

## 구장·훈련 시설·버스 운영 이력

공통 `clubFacilityHistory(kind, tid, label, stage, snapshot)`를 `development/39_facilities.js`에 두고 실제 착공·완공·개장·버스 교체 시점에 명시한 구단의 연대기로 기록한다. 비용, 목표 단계, 당초 완공 예정일과 실제 완료일을 문자열 스냅숏으로 남기며, 구단·시설·단계·예정일·사건 종류를 조합한 `source`로 동일 사건의 중복을 막는다. 현재 공사 배열이나 최근 리그 기사만 보관 수단으로 사용하지 않는다.

- `39_facilities.js`: 현금·예산으로 훈련 시설을 착공한 시점, 실제 완공, 구단 버스 실제 구매와 교체.
- `66_fac_ai.js`: AI의 실제 훈련 시설 투자 확정·착공과 완공. 이직 뒤 옛 구단에 남긴 공사도 옛 구단 기록으로 완공된다. 야인 기간 전 구단은 기존 `facDaily` 처리에 같은 후크가 적용된다.
- `finance/55_capex.js`: 모기업 투자나 지자체 분담이 승인되어 공사 상태가 생성된 시점만 착공으로 기록한다. 보류·거절된 요청과 신구장 규모 선택 전 계획을 착공으로 만들지 않는다.
- `finance/37_stadium.js`: 사용자·AI의 구장 시설 착공과 완공, 실제 신구장 착공과 개장. 사용자만 기록하던 완공·개장 분기를 공통 후크로 옮겨 AI 및 이직·사임 후 원 구단의 사건도 기록한다. 기존 우승 반지 수여식 기록은 유지했다.

AI 구장 공사의 실제 지출액 `c`, 지자체 분담 공사의 총 공사비 `totalC`를 공사 상태의 기록용 메타데이터로 보존한다. 지자체 공사의 기존 `c`는 구단 부담분으로 유지하여 환급·회계 동작을 바꾸지 않았다. 신구장의 `cost`는 규칙상 구단 분담금이므로 해당 문구로 표시한다. 경제 효과·공사 기간·AI 결정과 난수 호출은 변경하지 않았다.

추가 검증: `node tools/check-club-facilities-history.cjs` — **11개 통과**. 현금 훈련 공사, capex 거절/승인 구분, AI 시설 실제 투자, 이직·야인 뒤 옛 구단 완공, 버스 실제 지출과 중복 구매 거절, 구장 현금·지자체 분담 공사, AI 구장 투자, 신구장 계획·착공·개장 구분과 이직 뒤 개장, 리그 기사 삭제와 JSON 복원 후 영속 기록을 확인했다. 메모리 빌드만 사용했다.
