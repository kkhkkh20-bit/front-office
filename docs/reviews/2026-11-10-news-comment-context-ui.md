# 기사 본문·댓글 UI 독립 검수

## 기존 화면 조사

`src/ui/matches/22_pbp.js`의 `newsItem(n, full)`은 하나의 기사 객체에서 제목·본문·댓글을 함께 생성한다. `UI.nco`에는 기사 id별 펼침 여부만 저장하며, 목록 인덱스로 다른 기사의 댓글을 재사용하는 캐시는 없었다. `ourNewsView`의 분류·페이지 변경도 같은 기사 객체를 넘긴다.

팬 게시판의 기사 글은 별도로 `newsBank`와 `fComments`를 호출해 댓글을 생성하고 있었다. 기사 화면의 `newsComments`와 변수·분위기 결정이 달라 같은 기사에 다른 반응을 만들 수 있는 구조다. 이 경로와 발행 이후 `G.user`·현재 우승팀·선수 정보에 의존하는 문제를 엔진 담당에게 전달했다.

## 실제 브라우저 검사

`tools/check-news-comment-context-ui.cjs`는 소스를 메모리에서 빌드하며 출력 파일을 쓰지 않는다. `NEWS_HTML`을 지정하면 비교할 기존 HTML을 검사한다.

기존 배포 HTML에서 390×844, 768×1024, 1366×900 모두 다음 동작을 확인했다. 기사 6개의 댓글 펼침·접기, 모바일 필터 펼침·분류 변경, 대응 팬 게시판 글 열기, JSON 저장 복원 뒤 같은 기사 id 다시 열기에서 제목·본문·댓글의 연결이 유지됐다. 기사 선택이나 캐시 혼선은 재현하지 못했다. 클릭 간격은 기존 400ms 중복 터치 방지보다 길게 둔다.

새 검사는 우승 후보 분석을 우승 결과로 보지 않기, 부상 복귀를 새 부상으로 보지 않기, 미합의 FA 협상을 계약 완료로 보지 않기, 다른 구단 우승 구분, 발행 이후 구단 별칭·연고지, 선수 이름·소속·현재 우승자·팬 여론 변경과 저장 복원에도 기사 맥락과 전체 댓글 유지까지 확인한다. 타구단 우승은 우승 반응(`champ`)과 실제 대상 구단 `tid`를 함께 검증하며 현재 사용자 구단으로 치환하지 않는다.

제품 UI 소스는 이 독립 검수에서 변경하지 않았다.

## 수정 후 최종 결과

`CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium REVIEW_OUT=/tmp/news-comment-context-ui node tools/check-news-comment-context-ui.cjs` — 새 엔진을 포함한 메모리 빌드에서 390×844, 768×1024, 1366×900 모두 통과했다.

위의 기사 의미·구단/선수 출처 검증, 접힌 댓글 미리보기, 실제 펼침·접기, 분류 전환, 기사별 팬 게시판 댓글·대상 구단의 일치, JSON 복원을 확인했다. 발행 후 현재 여론·우승자·참조 선수의 이름과 소속을 변경하고 다시 JSON 복원해도 발행 맥락과 전체 댓글이 유지됐다. 페이지 오류와 가로 넘침은 없었다. 390px 결과 이미지를 직접 열어 기사와 해당 댓글이 함께 표시되는 것도 확인했다. 이미지 세 장은 `/tmp/news-comment-context-ui/`에 저장했다.

최종 보완 후에는 기사 8개로 다시 검사했다. `우승 확정?`처럼 의문형인 제목과 제목은 우승 확정이지만 본문에는 최종전이 남아 미확정이라고 명시한 기사를 각각 중립 반응으로 검증했다. 모든 구단의 `city`·`nick`도 변경하여 댓글 닉네임까지 포함한 전체 반응이 발행 당시와 같은지 검사했다.
