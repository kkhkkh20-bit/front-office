## 파일 및 협업 경계

이 담당은 `17_scouting.js`, `63_draft_claim.js`, `88_draft_view.js`, `31_draft_board.js`, `12_scout_area.js`의 `amScore` 캐시 범위를 수정했다. `53_gm_schedule.js`의 `gmObserve(p)` 호출은 해당 파일 소유 담당에게 요청하여 반영했고, `11_founding_draft.js`의 `dEst` 출처 메타데이터도 소유 담당이 추가했다. 학교 파일·에셋·빌드 출력은 변경하지 않았다.

## 검증

현재 소스를 `build({write:false})`로 읽는다. 15개 검사는 실제 `draftClaims`/행 툴팁, 당일 `schAdd` 전후 보고서와 캐시, 같은 조건의 다른 저장 및 저장 내부 성적 변경, `mvLog`/타팀 방출, 관찰 전후, 실제 `doPick`→이적→`switchTeam`, 원구단 초기 평가/옛 저장, 실제 `gmScoutTrip` 이틀 연속 실행과 저장 복원을 확인한다. 학교 친분 20→23→26과 직접 관찰 1→2를 함께 검사한다.

## 추가 성능 확인

수정 후 캐시 의존값을 매 조회에 확인하는 비용을 별도로 측정했다. `build({write:false}).html`을 로컬 Chromium에 메모리로 넣고, 1440×1000에서 후보 140명·3지역 활성 스카우트로 각 작업을 세 차례 수행했다. 전체 보드는 아마 성적 정렬·`more=DRAFT_POOL`로 실제 `draftBoard()` HTML을 DOM에 넣고 레이아웃 조회까지 포함했다. 외부 HTTPS 리소스는 차단하여 네트워크 대기와 분리했다.

| 작업 | 1회차 | 2회차 | 3회차 |
| --- | ---: | ---: | ---: |
| 전체 후보 `draftClaim` 140회 | 84.8ms | 45.1ms | 40.0ms |
| 전체 후보 `draftView` 140회 | 43.5ms | 41.2ms | 42.2ms |
| 아마 성적 비교함수로 140명 정렬 | 32.6ms | 27.1ms | 26.2ms |
| 140명 전체 보드 DOM 렌더·레이아웃 | 91.2ms | 49.0ms | 39.7ms |

렌더 결과는 약 166KB였다. 요청된 500ms 이상 지연 기준에 해당하지 않아 추가 생산 코드 최적화는 하지 않았다. 이는 해당 환경의 절대 실행 시간이며 이전 버전 대비 속도 향상이나 모든 모바일 기기의 성능을 입증하는 측정은 아니다. 필요하면 다음 단계에서 한 렌더 안의 `amScore`/`draftClaims` 조회를 배치 snapshot으로 공유하되, 학교 친분·저장 전환 무효화 정확성을 유지할 수 있다.
