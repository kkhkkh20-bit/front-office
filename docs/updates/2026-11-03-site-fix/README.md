# Cloudflare 사이트의 이전 2D 화면 문제

사용자는 `https://fronttime.kkhkkh-20.workers.dev/`에서 이전 2D 화면을 보고 있었다. GitHub main에 3D 코드를 올렸다는 사실을 실제 사이트 배포 완료로 안내한 것이 잘못이었다.

기존 Cloudflare 명령은 단독 다운로드용 `index.html`을 `site/index.html`로 그대로 복사한다. 3D 모델을 포함한 이 파일은 33,853,841 bytes였다. Wrangler 4.156.2의 실제 코드에서 정적 파일 한도가 `25 * 1024 * 1024` bytes임을 확인했으며, 기존 복사 방식의 크기 검사는 실패했다. 이 구성에서는 새 파일을 업로드하지 못하고 이전 배포가 남을 수 있다. 실제 원격 배포 로그는 이 작업 환경에서 읽지 못했다.

## 수정

- Cloudflare용 HTML과 모델을 분리했다. 사이트 HTML 약 7.1 MB, 가장 큰 모델 9,013,792 bytes로 모든 파일이 25 MiB 이하다.
- `wrangler.jsonc`의 custom build가 의존성 설치와 `tools/build-site.cjs`를 실행한다. 대시보드에 예전 복사 명령이 남아 있어도 업로드 전에 올바른 `site/`를 다시 생성한다.
- 모델은 같은 사이트에서 경기 화면을 열 때 내려받는다. 파일명에 내용 해시를 넣어 버전별 캐시를 분리한다. 문서에는 재검증 정책, 모델에는 장기 캐시 정책을 설정한다.
- `/release.json`에 배포 빌드 식별자와 파일 목록을 제공한다.
- 3D 실패 시 2D 화면 위에 이유와 “3D 다시 시도” 버튼을 표시한다. 다시 시도해도 날짜·경기·재생 위치는 유지한다.
- 다운로드용 `index.html`은 모델을 포함하는 단일 파일로 유지한다. 저장 슬롯·저장 키·사이트 주소는 바꾸지 않았다.

## 검증

- 사이트 크기·모델 주소·배포 명령·캐시 정책·단독 파일 보존 단위 검사 통과.
- 실제 배포 구성으로 브라우저에서 3D·공별 재생·같은 출처 모델 5개·모델 지연 로드 확인.
- 모델을 일부러 404로 응답해 안내와 재시도 버튼을 확인한 뒤, 정상 파일을 돌려주어 같은 경기와 재생 시점으로 복구하는 검사 통과.
- `WRANGLER_SEND_METRICS=false CI=1 npm exec --yes --package=wrangler@4.156.2 -- wrangler deploy --dry-run --outdir /tmp/front-office-worker-dryrun` 통과. 실제 custom build 실행과 자산 디렉터리 읽기까지 확인했으며 원격 업로드는 하지 않았다.
- 단위 검사 9개와 정적 점검 통과.
- 단독 HTML의 기존 3D 중계 4개 해상도·재생·중지·타구 추적·상세 복귀·외부 에셋 요청 없음·WebGL 대체 처리 검사 통과.

이 실행 환경은 위 workers.dev 주소 접속을 네트워크 정책으로 차단한다(`Tunnel connection failed: 403 Forbidden`). 따라서 원격 사이트의 새 배포 완료를 직접 확인했다고 말할 수 없다. main 푸시는 기존 자동 배포를 트리거하며, 실제 배포 버전은 사이트의 `/release.json`에서 확인해야 한다.
