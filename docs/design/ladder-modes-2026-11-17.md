# 경쟁 모드 기획: 같은 시드 챌린지 · 비동기 단장 대전 (2026-11-17)

범위: 기획과 측정만 다룹니다. 게임 코드는 바꾸지 않았습니다. 측정 스크립트 `tools/measure-ladder.cjs`만 추가했습니다.

이 게임은 시뮬레이션입니다. 사용자는 경기를 직접 하지 않고, 결과는 운영 결정과 큰 난수에서 나옵니다. 그래서 경쟁 모드는 다음 세 가지를 지켜야 합니다.

1. **실력이 보여야 합니다.** 무엇을 잘해서 이겼는지 결과 화면에서 읽혀야 합니다.
2. **운은 공평해야 합니다.** 운을 없앨 수는 없습니다. 모두가 같은 운을 받거나, 운이 평균으로 묻힐 만큼 판 수가 많아야 합니다.
3. **설명이 한 줄이어야 합니다.**

## 1. 결정성 진단

### 1-1. 난수 구조

- `src/core/random.mjs`의 `createRandom(random)`이 `R·rnd·ri·gauss·N·pick·rr`를 만듭니다. `src/engine/runtime/00_base.js`가 `FrontOfficeCore.createRandom(Math.random)`으로 **기본 `Math.random`을 넣습니다**. 시드도 상태 저장도 없습니다.
- 검사 도구(`tools/check-logic.js`, `check-sim.js`)는 엔진을 읽기 전에 `Math.random`을 mulberry32로 바꾸고 `__seed`로 시드를 정합니다. 그래서 검사에서는 결정적이고 브라우저에서는 아닙니다.
- 일부 기능은 이미 따로 시드를 씁니다: `seededRand(문자열)`(얼굴, 투구 폼, 벤치 클리어링 `bench:${day}:${home}:${away}`, 구단주 성향), 중계 연출 `mulberry(day·k·home·away)`(`21_cast.js`). 이 방식은 결정적이고 엔진 흐름을 건드리지 않습니다. **경쟁 모드의 난수 분리(2-3절)는 이 방식을 넓히는 일입니다.**

### 1-3. 한 번의 다른 결정이 시즌을 통째로 바꿉니다

엔진은 **난수 흐름이 하나**입니다. 결정 하나가 난수를 한 개만 더 써도 그 뒤의 경기, 부상, 성장, 소식이 전부 다른 값을 받습니다. 측정(시드 7, 결정은 모두 같음, 10일째에 난수만 더 씀):

| 더 쓴 난수 | 우리 구단 | 순위 | 우승 구단 |
| --- | --- | --- | --- |
| 0개 | 67승 73패 4무 | 6위 | 4번 |
| 1개 | 56승 85패 3무 | 10위 | 3번 |
| 2개 | 55승 87패 2무 | 9위 | 4번 |
| 3개 | 54승 81패 9무 | 9위 | 5번 |

결정은 하나도 다르지 않은데 승수가 54~67승으로 13승 차이 납니다. 한 시즌 144경기의 이항 운(표준편차 약 6승)과 부상·성장 연쇄가 겹친 결과입니다.

같은 시드를 줘도 결정이 하나만 다르면 **운이 공유되지 않습니다.** 첫 트레이드 하나로 시즌 운이 새로 뽑힙니다. 같은 시드 챌린지가 공평하려면 난수 흐름을 나눠야 합니다(2-3절).

### 1-4. 결정 기록(리플레이 로그)

- 화면 조작은 `src/ui/actions/41_guard_boot.js`의 클릭 처리 하나가 `A[이름](값)`으로 보냅니다. 화면 코드의 `data-a` 이름은 652종, `A.` 호출 이름은 117종입니다. 대부분은 탭 이동 같은 보기 조작입니다.
- 기록 방식: **상태를 바꾸는 동작만** `{d: 게임 날짜, a: 동작 이름, v: 값, i: 입력값}`으로 남깁니다. 보기 조작은 기록하지 않습니다. 화면 입력칸(연봉 제시액 등)은 동작이 읽는 값을 함께 남깁니다.
- 크기 추정(측정 아님): 한 시즌에 상태를 바꾸는 조작 100~500개 × 약 30바이트 = 3~15KB, 압축하면 1~5KB. 3시즌이어도 저장(2.7MB)보다 수백 배 작습니다.
- 재생 비용(측정 기준): 새 게임 7~14초 + 1년 51~94초. **3시즌 한 건을 다시 돌리는 데 약 3~5분**입니다.
- 위험: 동작이 `UI` 상태(열린 시트, 선택 목록)를 읽는 경우가 많습니다. 로그만으로 같은 입력을 만들려면 "동작 = 엔진 호출 + 인자"로 정리된 층이 필요합니다. 전부 정리하는 데 L 규모입니다. 그래서 1차는 **리플레이 검증을 상위권 표본 점검에만** 씁니다(2-4절).

### 2-3. 실력과 운

**실력이 드러나는 곳.** 이 게임에서 단장의 실력은 다음입니다.

| 실력 | 보이는 결과 |
| --- | --- |
| 창단 지명·FA·트레이드 판단 | 같은 돈으로 만든 전력(`teamRating`), 승수 |
| 육성(훈련, 코치, 2군 기용) | 3년 동안 오른 국내 선수 능력 합(육성 가치) |
| 재정(연봉, 시설, 관중) | 3년 순이익과 남은 현금 |
| 사람 관리(감독, 구단주, 선수 사기) | 구단주 신뢰, 경질 여부 |

**운을 공평하게 만드는 방법.** 1-3절처럼 결정 하나가 시즌 운을 새로 뽑으면, 같은 시드는 시작 화면만 같을 뿐입니다. 그래서 난수를 **용도별 흐름**으로 나눕니다.

| 흐름 | 시드 | 효과 |
| --- | --- | --- |
| 경기 | `hash(챌린지 시드, 날짜, 홈, 원정)` | 같은 날 같은 대진은 같은 공 순서를 받음. 전력이 같으면 결과도 같음 |
| 부상 | `hash(시드, 연도, 선수 id, 경기 순번)` | 트레이드 한 번으로 남의 부상이 바뀌지 않음 |
| 성장 | `hash(시드, 연도, 선수 id)` | 같은 선수는 같은 겨울을 보냄. 차이는 코치·훈련·기용에서만 나옴 |
| 신인·외국인 시장 | `hash(시드, 연도, 주차)` | 모두에게 같은 후보가 나옴 |
| AI 구단 판단 | `hash(시드, 날짜, 구단)` | 다른 구단의 반응은 우리 결정에 따라서만 바뀜 |

이렇게 하면 같은 운을 모두가 나눠 받고, 순위 차이는 결정에서 나옵니다. 남는 운(우리 결정으로 대진·선수가 바뀐 뒤의 운)은 점수 설계로 줄입니다.

**점수(한 줄로 보여 줌: "단장 점수 1,234점").**

| 구성 | 비중 | 이유 |
| --- | --- | --- |
| 3시즌 정규시즌 승률 | 40% | 가장 알기 쉬움. 3시즌 합(432경기)이라 한 시즌보다 운이 작음(한 시즌 승수의 운 폭은 표준편차 약 6승) |
| 가을야구·우승 | 15% | 진출 +, 한국시리즈 +, 우승 +. 단기전 운이 커서 비중을 낮춤 |
| 육성 가치 | 20% | 3년 뒤 25세 이하 국내 선수 능력 상승 합 |
| 재정 | 15% | 3년 순이익(구단 규모로 나눔) |
| 구단주 신뢰 | 10% | 경질되면 그해부터 0점 |

- 점수표는 결과 화면에서 다섯 줄로 보여 줍니다. "어디서 이겼는지"가 보이게 합니다.
- **기대 대비 점수(선택):** 같은 시드를 서버에서 "기본 결정"으로 한 번 돌려 기준선을 만들고, 승률은 기준선과의 차이로 매깁니다. "AI 단장보다 몇 승 더"는 설명하기 쉽습니다.
- **월간 챌린지는 시드 3개:** 같은 규칙으로 세계 3개를 각 1시즌. 점수는 평균. 시드 하나의 대박·쪽박을 줄입니다.

### 2-4. 부정 방지(클라이언트 게임이라는 한계 포함)

| 방법 | 막는 것 | 못 막는 것 | 규모 |
| --- | --- | --- | --- |
| 저장 안 잠금 표시(`G.chal={id,seed,lock:true}`) + 잠긴 기능 끔 | 실수로 하는 에디터·난이도 변경 | 개발자 도구로 `G`를 직접 고치기 | S |
| 제출에 결과 요약 + 저장 해시 + 결정 로그 | 기록 부풀리기(요약과 저장이 안 맞으면 거절) | 처음부터 끝까지 고친 저장 | S |
| 개연성 검사(서버) | 승률 .800 초과, 능력 상한 초과, 연봉 합 > 한도, 시즌 길이 이상 | 그럴듯하게 고친 기록 | S |

솔직하게: **브라우저에서 도는 게임은 결과를 완전히 믿을 수 없습니다.** 순위 1~20위만 리플레이로 확인하고, 나머지는 개연성 검사와 신고로 처리합니다. 상금이나 유료 보상을 걸면 안 됩니다. 칭호·배지 정도가 맞습니다.

리플레이 검증 실행 위치: Cloudflare Worker는 무료 플랜 CPU가 요청당 10ms, 유료도 최대 5분이라 3시즌(3~5분) 재생에 맞지 않습니다. **GitHub Actions 예약 작업**(주 1회, 상위 20건 × 약 4분 = 약 80분)이 맞습니다. 공개 저장소면 무료, 비공개면 월 2,000분 무료 한도 안입니다.

### 2-5. 서버

`worker/index.js`의 패턴(같은 출처만, IP 해시 횟수 제한, `not_configured` 503, 저장 형식 검사)을 그대로 씁니다.

비용(2026-10 Cloudflare 공개 요금 기준, 운영 전 다시 확인 필요):

## 3. 2안 — 비동기 단장 대전

### 3-1. 한 줄 설명과 참고

> **"내 구단을 등록해 두면, 다른 단장의 구단과 매일 밤 30경기씩 자동으로 맞붙습니다."**

참고: 컴투스프로야구 매니저(구단 등록 후 자동 리그전, 등급), OOTP Perfect Team(카드 구단 리그, 시즌제), 판타지 야구 샐러리캡 리그.

### 3-2. 규칙

**구단을 어디서 가져오나.** 두 방식이 있고 성격이 크게 다릅니다.

| 방식 | 내용 | 장점 | 문제 |
| --- | --- | --- | --- |
| A. 커리어 구단 등록 | 내 저장의 1군 명단·감독·운영 방침을 그대로 등록 | 내가 키운 구단이라 애착이 큼 | 오래 한 저장이 압도적(10년 차 왕조 대 1년 차). 저장을 고치기 쉬움. 검증 불가 |
| **B. 예산 드래프트 구단** | 시즌마다 공통 선수 풀(서버가 정한 세계)에서 연봉 한도 안으로 29명을 뽑고, 감독·타순·선발 순서·불펜 역할을 정함 | 모두 같은 조건. 서버가 풀과 한도로 완전히 검증 가능. 과금·플레이 시간과 무관 | 커리어와 따로 놉니다 |

권장: **순위전은 B**, A는 친구 대전(순위 없음)으로만.

| 항목 | 규칙(B 기준) |
| --- | --- |
| 시즌 | 4주. 시즌마다 새 선수 풀과 연봉 한도 |
| 구단 | 1군 엔트리 29명(게임 규칙 `ENTRY_BASE`와 같음), 연봉 합 한도(예: 리그 평균 1군 연봉 합), 외국인 한도는 본게임 규칙, 감독 1명(풀에서) |
| 운영 방침 | 타순 규칙, 선발 5인 순서, 마무리·필승조, 대타·대주자 성향, 수비 위치. 경기 중 조작 없음 |
| 대전 | 하루 1회, 서버가 짝을 지어 **30경기 시리즈**(홈 15·원정 15) |
| 수정 | 명단·방침은 언제나 수정 가능. 다음 대전부터 적용 |
| 부상·피로 | 시리즈 안에서만 적용하고 시리즈가 끝나면 초기화 |

### 3-3. 실력과 운

**실력:** 한도 안에서 가성비 좋은 선수 고르기, 포지션·좌우 균형, 선발·불펜 배분, 감독 성향과 명단의 궁합, 상대 분포(메타)에 맞춘 조정.

**운 처리:**

| 장치 | 내용 |
| --- | --- |
| 시리즈 길이 30경기 | 전력 차 2.6에서 강한 쪽이 91% 이김. 7경기는 75%뿐(0절 표) |
| Glicko-2 점수 | 시리즈 결과를 승률(예: 18승 12패 = 0.60)로 넣음. 한 시리즈 운이 점수에 작게만 반영. 비슷한 전력끼리 판정은 여러 날에 걸쳐 쌓임 |
| 등급 | 브론즈·실버·골드·다이아·챔피언. 점수 구간으로 정하고, 시즌 끝에 한 등급 아래로 초기화 |
| 짝짓기 | 점수가 가까운 상대 우선. 같은 상대와 시즌에 3번 이하 |
| 시드 공개 | 시리즈 시드 = `hash(시즌, 날짜, 구단A, 구단B)`. 누구든 같은 결과를 다시 돌려 볼 수 있음 |
| 과금 없음 | 선수 풀과 한도가 모두에게 같음. 돈이나 플레이 시간으로 전력을 살 수 없음 |

### 3-4. 부정 방지

2안은 1안보다 훨씬 지키기 쉽습니다. **경기를 서버 쪽 실행기가 돌리기 때문입니다.**

| 공격 | 대응 |
| --- | --- |
| 결과 조작 | 사용자 기기는 경기를 돌리지 않음. 실행기가 돌리고 결과만 공개 |
| 능력치를 고친 선수 | B 방식은 선수 id만 받음. 능력은 서버 풀에서 읽음 |
| 한도 초과 | 서버가 연봉 합·인원·포지션을 검사 |
| 여러 계정으로 점수 올리기(서로 져 주기) | 시리즈를 실행기가 정하므로 져 주기가 어려움. 같은 기기 번호끼리는 짝을 짓지 않음 |
| A 방식(커리어 구단) | 검증할 수 없음. 그래서 순위 없이 친구 대전으로만 |

### 3-5. 서버와 실행기

**Worker 안에서 경기를 돌리지 않습니다.** 근거:

- 30경기 시리즈 = 약 0.2~0.5초 CPU. Worker 무료 플랜은 요청당 CPU 10ms입니다.
- `simGame`은 세계 전체(`G`: 리그 규칙, 구장, 감독, 날짜)를 전제로 합니다. 세계를 만드는 데 7~14초, 저장을 읽어도 JSON 2.6MB입니다.
- 엔진 3.2MB(gzip 1.17MB)는 Worker 크기 한도(무료 3MB, 유료 10MB, 압축 기준) 안이지만, 위 두 가지 때문에 맞지 않습니다.

**실행 구조:**

1. **대전용 기준 세계** 하나를 시즌마다 만들어 둡니다(고정 시드, 저장 2.6MB). 선수 풀도 여기서 나옵니다.
2. 매일 밤 **GitHub Actions 예약 작업**이 끝점에서 오늘의 짝을 받아 엔진을 노드로 돌립니다. 기준 세계의 두 구단 자리에 등록 구단을 넣고 `simGame(day, 홈, 원정)` + `applyGame`을 30번 돌립니다(`options.sides`로 명단을 직접 넘길 수도 있음).
3. 결과(승패, 시리즈 요약, 주요 선수 기록)를 Worker에 올립니다. Worker는 Glicko를 갱신합니다.

처리량(측정 기준): 경기당 6~8ms → 30경기 약 0.25초. 구단 1,000개가 하루 1시리즈씩 = 500시리즈 × 30경기 = 15,000경기 ≈ **2~4분**. GitHub Actions 무료 한도 안입니다. 구단이 1만 개를 넘으면 전용 실행기(작은 VPS)를 검토합니다.

| 끝점 | 내용 |
| --- | --- |
| `GET /api/duel/season` | 시즌 정보, 연봉 한도, 선수 풀 주소(정적 JSON) |
| `PUT /api/duel/club` | `{nick, device, roster:[id…29], mgr, plan}` 등록·수정 |
| `GET /api/duel/me?device=` | 내 점수, 등급, 최근 시리즈 10개 |
| `GET /api/duel/series/:id` | 한 시리즈의 경기별 점수, 주요 기록, 시드 |
| `GET /api/duel/board?tier=` | 등급별 상위 100 |
| `POST /api/duel/results`(실행기 전용, 비밀 키) | 오늘 결과 묶음 |

데이터 크기: 등록 구단은 선수 id 29개 + 방침이라 1KB 안팎입니다(A 방식으로 능력치까지 보내면 측정상 LZ 64~86KB). 선수 풀(약 700명)은 정적 파일로 한 번만 받습니다.

비용: 등록·수정이 하루 1,000회를 넘으면 KV 무료 쓰기 한도를 넘습니다. **D1을 권합니다**(무료 하루 10만 행 쓰기). 실행기 결과 쓰기는 하루 한 번 묶음입니다.

개인 정보: 1안과 같습니다. 닉네임과 기기 무작위 번호만.

### 3-6. 화면

- 처음 화면에 **"단장 대전"** 버튼 하나.
- 화면 넷.
  1. **대전 홈**: 내 등급·점수, 오늘 상대, 어젯밤 결과 한 줄("18승 12패, +14점"), "구단 고치기".

## 6. 단장님이 정할 것

1. **무엇부터 할지:** 1안(게임다운 경쟁, 엔진 작업 많음)과 2안(지키기 쉬움, 명단 짜기 위주) 중 먼저 할 것.
2. **1안 길이:** 주간 3시즌(3~6시간)인지, 더 짧은 1~2시즌인지. 월간을 둘지.
3. **1안 시작 조건:** 구단을 지정할지(모두 같은 구단), 창단 지명부터 하게 할지(같은 풀에서 지명 순번 지정).
4. **1안 점수 비중:** 승률·가을야구·육성·재정·신뢰 비중(초안 40·15·20·15·10)과 "AI 단장 대비 점수"를 쓸지.
5. **2안 구단 방식:** 순위전을 예산 드래프트(B)로만 할지, 커리어 구단(A)도 순위에 넣을지.
6. **서버 비용:** Cloudflare 유료($5/월)와 D1 사용, GitHub Actions 예약 작업(저장소 공개 여부에 따라 무료 한도가 다름).
7. **보상:** 칭호·배지만 줄지(권장), 본게임에 영향을 주는 보상을 줄지(부정 동기가 커짐).
8. **닉네임:** 닉네임만 받는 익명 방식으로 충분한지, 나중에 계정이 필요한지.

## 7. 권장

**2안(단장 대전, 예산 드래프트 방식)을 먼저 합니다.** 이유는 셋입니다.

1. 경기를 서버 쪽 실행기가 돌려 부정 방지가 처음부터 됩니다. 1안은 리플레이 검증과 브라우저 간 결정성이 먼저 해결돼야 공정해집니다.
2. 운 문제가 숫자로 풀립니다. 30경기 시리즈와 Glicko면 측정한 전력 차 2.6에서 강한 쪽이 91% 이깁니다. 1안은 결정 하나로 시즌 운이 새로 뽑히는 문제(1-3)를 난수 분리(L)로 고쳐야 합니다.
3. 엔진 작업이 시드형 난수 하나로 끝납니다. 이 작업은 1안의 0단계와 같아서 그대로 다음 단계의 바탕이 됩니다.

1안은 그다음에 "시드형 난수 → 조회 난수 제거 → 교차 브라우저 시험 → 모드 잠금" 순서로 엽니다. 첫 판은 칭호만 걸고 상위 20위 수동 검증으로 시작합니다. 난수 분리가 끝나면 정식 순위로 바꿉니다.
