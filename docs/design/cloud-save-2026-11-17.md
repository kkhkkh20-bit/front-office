## 0. 배경

카페 제보(11-17): "A기기·B기기에서 같은 계정을 사용. A기기에서 12/27까지 플레이 → B기기로 넘어가 1/10까지 플레이 → 다시 A기기로 가면 12/27부터 플레이하게 됩니다."

- 지금 게임에는 **계정 저장이 없습니다.** 저장은 기기 브라우저(localStorage·IndexedDB, `src/ui/runtime/00_core.js`의 `SaveStore`)에만 남습니다. itch.io 계정이나 래더 닉네임과도 연결되지 않습니다.
- 기기 옮기기(`/api/transfer`, `docs/save-transfer.md`)는 8자리 코드로 **한 번 복사**하는 기능입니다. A에 있던 옛 슬롯은 그대로 남으므로 A로 돌아가면 옛 저장이 열립니다.
- 11-17에 먼저 한 일(옵션 1·2): 저장이 기기마다 따로라는 안내를 화면에 적었습니다. 기기 옮기기로 받은 저장이 같은 게임(세계 번호 `G.wid`) 슬롯과 겹치면 날짜·저장 시각을 나란히 보여 주고, "그 슬롯을 받은 저장으로 바꾸기"를 고르게 했습니다. 이 문서는 그다음 단계인 **계정 클라우드 저장**(옵션 3)입니다.

목표: 같은 사람이 여러 기기에서 **코드 없이** 마지막 진행을 이어 합니다. 어떤 경우에도 더 최근 저장을 옛 저장이 말없이 덮지 않습니다. 오프라인에서도 지금처럼 플레이할 수 있어야 합니다.

## 1. 로그인(같은 사람 알아보기)

서버 v1(`worker/v1`, D1)에는 이미 플레이어(`players`)와 기기 토큰(`devices`, `ft1.` + 32자, 서버에는 SHA-256만)이 있습니다. 다만 웹에서 **다른 기기를 같은 플레이어에 붙이는 길이 없습니다.** `POST /player/login`은 스팀·구글 플레이 게임즈 확인이 필요하고, 비밀값이 없어 501입니다.

| 방식 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. 기기 연결 코드(권장, 웹 1단계)** | 이미 쓰는 기기에서 "다른 기기 연결" → 서버가 10분짜리 일회용 코드(8자리, 기기 옮기기와 같은 글자표) 발급 → 새 기기가 코드 입력 → 그 기기에 같은 플레이어의 새 기기 토큰 발급(`devices` 한 줄) | 외부 계정·비밀값이 필요 없음. 지금 표(`devices`)를 그대로 씀. 기기 목록·연결 끊기도 쉬움 | 토큰을 잃으면(브라우저 데이터 삭제) 다른 연결된 기기에서 다시 코드를 만들어야 함. 연결된 기기가 하나뿐인데 잃으면 복구 불가 → "복구 코드"(긴 무작위 문자열, 한 번만 보여 줌)를 함께 제공 |
| B. 구글/스팀(앱 낼 때) | 앱 출시 때 이미 설계된 `player/link`·`player/login` | 기기를 잃어도 같은 계정으로 복구 | 웹에는 해당 없음. 구글 웹 로그인(OAuth)을 따로 붙이면 개인정보·심사 부담이 커짐 |
| C. 이메일 매직 링크 | 이메일로 로그인 링크 | 친숙함 | 메일 발송 서비스·개인정보(이메일) 보관이 생김. 지금 방침(이름·이메일을 받지 않음)과 어긋남 |

권장: **A로 시작하고, 앱을 낼 때 B를 같은 플레이어에 붙입니다.** 연결 API(제안):

- `POST /api/v1/player/pair` (토큰 필요) → `{code, expiresAt}` (10분, KV `pair:CODE` → player_id, 한 번 쓰면 삭제)
- `POST /api/v1/player/pair/claim {code, platform}` → `{player, token}` (IP당 시간당 시도 제한, 틀린 코드는 화면이 2·4·8…초 대기)
- `GET /api/v1/player/devices` · `DELETE /api/v1/player/devices/:id` (연결 끊기. 끊긴 토큰은 바로 401)

래더를 이미 쓰는 기기는 그 플레이어로, 아니면 처음 "클라우드 저장 켜기" 때 익명 플레이어를 만듭니다. 한 기기에 익명 플레이어가 따로 있었는데 다른 플레이어로 연결하면 기존 v1 규칙처럼 합치지 않습니다(래더 기록은 옛 플레이어에 남음, 화면에서 알림).

## 2. 저장소와 크기·비용

저장 크기: 브라우저 저장 형식(deflate, `z15`)으로 슬롯 하나가 **수백 KB~수 MB**, 기기 옮기기 형식(LZ base64)으로는 최대 8MB까지 봤습니다. 클라우드에는 **deflate 바이트 그대로**(base64 없이) 올리면 LZ base64보다 대략 절반 이하입니다(정확한 비율은 1단계에서 실제 저장 표본으로 잴 것).

| | Workers KV | D1 | **R2(권장: 본문)** |
| --- | --- | --- | --- |
| 값 하나 최대 | 25 MiB | 행·값 약 2MB → 쪼개야 함 | 사실상 제한 없음(한 번 올리기 5GB) |
| 무료 쓰기 | **하루 1,000회**(모든 키 합) | 하루 10만 행 | 월 100만 회(Class A) |
| 무료 저장 | 1GB | 5GB | 10GB |
| 일관성 | 최종 일관성(최대 약 60초 다른 지역에서 옛 값) | 강한 일관성(한 DB) | 강한 일관성(쓰기 후 읽기) |
| 조건부 쓰기 | 없음 | 트랜잭션·`WHERE rev = ?` | `onlyIf`(etag) 조건부 put |
| 유료 | 쓰기 100만 회/월 포함, 이후 100만당 약 $5 | 쓰기 월 5,000만 행 포함 | 저장 GB당 월 약 $0.015, 쓰기 100만 회당 약 $4.50 |

(한도·요금은 2026-11 Cloudflare 문서 기준 기억값입니다. 켜기 전에 다시 확인할 것.)

결론:
- **본문은 R2**(`saves/<player_id>/<slot>/<rev>.bin`, 최근 3판만 남기고 지움). 쪼갤 필요가 없고 조건부 쓰기도 됩니다.
- **목록·판번호는 D1** 표 `cloud_saves(player_id, slot, rev, wid, day, date_label, team, device_id, device_name, bytes, sha256, updated, PRIMARY KEY(player_id, slot))`. 판번호 비교·갱신을 한 문장(`UPDATE … WHERE rev = ?`)으로 원자적으로 합니다.
- KV는 하루 쓰기 1,000회 한도 때문에 본문 저장에는 쓰지 않습니다(이미 래더·대회·기기 옮기기가 나눠 씀).
- D1만으로 하려면 2MB 미만 조각(`cloud_chunks`)으로 나눠야 하고 쓰기 행 수가 조각 수만큼 늘어 비추천.

### 올리는 횟수(유저 한 명 하루)

게임은 0.7초마다 몰아 저장합니다(`save()`). 그대로 올리면 하루 수천 번이라 안 됩니다. 제안:

1. **기기를 떠날 때**: 탭 숨김·닫기(`visibilitychange` hidden, `pagehide`). 지금의 `saveFlush` 자리에서 `fetch(..., {keepalive:true})`. keepalive 본문은 64KB 제한이라 큰 저장은 실패할 수 있습니다 → 실패하면 다음 실행 때 "올리지 못한 진행이 있습니다"로 다시 올림.
2. **주기적으로**: 진행 중 **10분에 한 번**, 그리고 게임 날짜가 바뀐 경우에만.
3. **직접**: 설정 › 저장·기기의 "지금 클라우드에 저장" 버튼.
4. 처음 화면으로 나갈 때·슬롯을 바꿀 때 한 번.

예상: 하루 1시간 플레이 유저 ≈ 6~10회 올리기, 한 번에 평균 1MB. 하루 활성 1,000명이면 하루 약 1만 회·10GB 전송. R2 쓰기 월 약 30만 회(무료 100만 안), 저장은 유저당 슬롯 2개 × 3판 × 1MB ≈ 6MB → 1,000명 6GB(무료 10GB 안). D1은 올리기마다 1~2행이라 여유. **하루 활성 1,000명까지 무료 범위, 그 이상은 월 몇 달러** 수준으로 봅니다. 유저 한 명당 하루 올리기 상한(예: 200회)과 슬롯 수 상한(예: 클라우드 슬롯 3개)을 둡니다.

## 3. 프로토콜

### 판번호와 기기

- 슬롯마다 서버 판번호 `rev`(정수, 쓰기마다 +1). 서버가 정하며 기기 시계를 믿지 않습니다.
- 기기 번호 `device_id`(이 기기 토큰의 `devices` 행 id). 화면용 기기 이름(`device_name`, 예: "Windows · Chrome", 사용자가 바꿀 수 있음).
- 기기는 슬롯마다 `base`(마지막으로 서버와 맞춘 판번호)를 슬롯 목록(`danjang-meta`)에 적어 둡니다.

### API (제안, 토큰 필요)

- `GET /api/v1/saves` → 슬롯별 `{slot, rev, wid, day, date, team, device_name, updated, bytes}` (본문 없음, 가볍게)
- `GET /api/v1/saves/:slot` → 본문(`application/octet-stream`), 머리글 `ETag: "<rev>"`, `X-Save-Day`, `X-Save-Device`
- `PUT /api/v1/saves/:slot` 본문 = deflate 바이트, 머리글 `If-Match: "<base>"`(새 슬롯은 `If-None-Match: *`), `X-Save-Day`, `X-Save-Wid`, `Content-Length`
  - 서버 rev = base → 저장, rev+1, `200 {rev}`
  - 서버 rev ≠ base → **`409 conflict`**, 본문에 서버 쪽 `{rev, day, date, device_name, updated}`. 덮지 않습니다.
  - `If-Match` 없는 요청은 받지 않습니다(`428 precondition_required`). 새 API라 예전 클라이언트가 없으므로 이전 호환 걱정이 없습니다.
- `DELETE /api/v1/saves/:slot` (`If-Match` 필요)

순서(R2와 D1 사이 원자성): ① D1에서 `rev = base` 확인 후 `pending` 표시 → ② R2에 `<rev+1>.bin` put → ③ D1 `UPDATE cloud_saves SET rev = rev+1 … WHERE player_id=? AND slot=? AND rev = ?`(바뀐 행이 0이면 409, R2 새 객체 삭제). 읽기는 D1의 rev가 가리키는 객체만 읽으므로 ②까지만 된 객체는 보이지 않습니다.

### 언제 비교하나

- 실행할 때, 처음 화면 **이어하기**·슬롯 열기 직전, 탭으로 돌아올 때(`visibilitychange` visible, 마지막 확인 뒤 1분 넘었을 때): `GET /saves`로 서버 판번호를 봅니다.
- 판단(슬롯마다):
  - 서버 rev = base, 이 기기에 올리지 않은 진행 있음 → 올림.
  - 서버 rev > base, 이 기기 진행이 base 이후 바뀌지 않음 → **서버 저장이 더 새것**: 바로 받아 열지 말고 한 줄로 묻습니다(기본 선택 = 받기).
  - 서버 rev > base, 이 기기도 바뀜 → **충돌**: 두 저장을 나란히 보여 주고 고르게 합니다.
  - 예전 저장(base 없음, 클라우드를 켠 첫 실행): 세계 번호가 같으면 게임 날짜(`day`)를 먼저, 같으면 저장 시각을 비교해 기본 선택을 정하되 **늘 묻습니다**.

### 묻는 화면

> 다른 기기에서 더 최근에 저장한 기록이 있습니다.
> · 클라우드: **2027년 1월 10일** · B기기(휴대폰 · Chrome) 11월 17일 오후 9:12 저장
> · 이 기기: **2026년 12월 27일** · 11월 16일 오후 11:40 저장
> [클라우드 저장으로 이어 하기] [이 기기 저장으로 이어 하기(클라우드를 덮음)] [이 기기 저장을 새 슬롯에 남기고 클라우드로]

- "이 기기 저장으로"를 고르면 그때 `If-Match: <서버 rev>`로 올립니다(사용자가 본 판번호. 그사이 또 바뀌었으면 다시 묻기).
- 이 기기 날짜가 클라우드보다 앞이면 그 버튼은 빨간색이고 두 번 눌러야 합니다(기기 옮기기 비교와 같은 규칙).
- 게임 중 409가 나면 진행을 멈추지 않고 위쪽 띠로 알립니다: "다른 기기가 이 슬롯을 더 최근에 저장했습니다. 이 기기 진행은 클라우드에 올리지 않습니다." 로컬 저장은 계속하고, 고를 때까지 올리지 않습니다.

### 오프라인

- 로컬 저장이 언제나 먼저입니다. 클라우드 실패(오프라인·5xx·429)는 게임을 막지 않고, 슬롯 목록에 "클라우드에 아직 올리지 않음" 표시만 둡니다. 연결되면 base와 함께 다시 올립니다(그사이 서버가 바뀌었으면 409 → 묻기).
- 내려받은 `index.html`(file://)·itch.io(다른 출처) 화면에서는 클라우드 저장 메뉴 자체를 숨깁니다(itch에서 쓰려면 `V1_ORIGINS`·CORS를 따로 정해야 함, 정할 것 참고).

## 4. 보안

- 토큰은 지금 v1 기기 토큰을 그대로 쓰고 서버에는 해시만. 저장 API는 그 토큰의 플레이어 것만 읽고 씁니다(경로에 player_id를 받지 않음).
- 같은 출처만(지금 `originOk`). 앱 출처는 `V1_ORIGINS`.
- 횟수 제한: 플레이어당 올리기 분당 6회·하루 200회, 받기 분당 30회, 연결 코드 받기 IP당 시간당 10회. 넘으면 429 + `Retry-After`.
- 크기 제한: 본문 16MB(deflate) 이하. 서버는 본문을 풀어 보지 않고(Worker CPU), 앞부분 형식과 길이만 확인. 받은 쪽은 지금처럼 `saveCheck`로 검사한 뒤에만 엽니다.
- 기기 연결 코드는 10분·한 번만·8자리(약 40비트) + 시도 제한. 연결 끊기·"모든 기기 로그아웃"(토큰 전부 삭제) 제공.
- 관리자도 저장 본문을 보지 않는 것이 원칙(관리자 API에 본문 읽기 없음). 지우기 요청(`DELETE /player`)은 R2 객체까지 지웁니다.

- 보관 항목 표에 추가: 저장 본문, 게임 날짜·구단 이름·세계 번호, 기기 이름, 올린 시각. 보관 기간: 클라우드 저장을 끄거나 플레이어를 지울 때까지, 마지막 접속 뒤 1년이 지나면 자동 삭제(제안).
- 처리 위탁에 Cloudflare R2 추가(전 세계 데이터센터, 저장 위치 힌트는 아시아·태평양).
- 켜기는 **사용자가 고를 때만**(기본 꺼짐). 켤 때 한 화면에서 무엇을 올리는지 알림.

## 7. 위험

- **덮어쓰기 사고**: 가장 큰 위험. 조건부 쓰기(`If-Match` 필수)와 "늘 묻기", R2 최근 3판 보관(실수로 덮어도 되돌릴 수 있게 "이전 판 받기")으로 막습니다.
- **떠날 때 올리기 실패**: 모바일 브라우저는 탭을 닫을 때 큰 요청을 자주 버립니다. 그래서 주기 올리기와 다음 실행 때 다시 올리기를 함께 둡니다. 그래도 마지막 몇 분은 빠질 수 있다는 것을 화면에 적습니다("클라우드 마지막 저장: 오후 9:02").
- **비용 폭주**: 버그로 올리기가 반복되면 R2 쓰기·전송이 늘어납니다. 플레이어당 하루 상한과 관리자 사용량 표시로 막습니다.
- **토큰 분실**: 브라우저 데이터를 지우면 그 기기 연결이 사라집니다. 다른 기기나 복구 코드가 없으면 클라우드 저장에 다시 닿을 수 없습니다(구글/스팀 연결 전까지).
- **저장 형식 변경**: 클라우드에는 로컬과 같은 형식(deflate)을 올리므로, 새 버전 저장을 옛 버전 게임이 받으면 열지 못할 수 있습니다 → 목록에 게임 버전을 함께 두고 "새 버전에서 저장한 기록입니다. 새로고침해 업데이트하세요" 안내.

## 8. 정할 것 (운영자)

1. 로그인 방식: 기기 연결 코드(권장)로 시작해도 되는지, 복구 코드를 둘지.
2. R2 버킷을 만들어도 되는지(무료 10GB, 넘으면 GB당 월 약 $0.015).
3. 클라우드 슬롯 수(제안 3개)와 판 보관 수(제안 3판), 장기 미접속 자동 삭제 기간(제안 1년).
4. itch.io 화면에서도 쓸지(쓰려면 itch 출처를 `V1_ORIGINS`에 넣고 CORS를 엶. 안 쓰면 itch에서는 지금처럼 기기 옮기기만).
5. 기본 켜짐/꺼짐(권장: 꺼짐, 사용자가 켬).
