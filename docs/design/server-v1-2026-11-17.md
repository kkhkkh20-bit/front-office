# 서버 v1 설계 (2026-11-17)

구단주 요청: "서버 필요한 것도 구축해줘. 장기적으로 플레이스토어와 스팀에도 적용될 수 있는 것으로."

이 문서는 프런트야구 서버의 첫 기반(v1)을 정리합니다. 코드는 `worker/v1/*`, 표는 `migrations/0001_init.sql`, 설정 순서는 `docs/server-setup.md`에 있습니다.

## 1. 요약

| 항목 | 결정 |
|---|---|
| 실행 위치 | 지금 쓰는 Cloudflare Worker `fronttime` 그대로. 새 경로 `/api/v1/*`만 추가합니다. |
| 관계형 데이터 | **Cloudflare D1**(SQLite). 플레이어·래더 시즌·순위표·리그 결과·맞대결·소식·일별 집계. |
| 덩어리·임시 데이터 | **Workers KV**(지금 그대로). 기기 옮기기 저장, 프런트컵 신청·결과, 예전 래더. |
| 캐시 | Cache API(`caches.default`, 무료). 순위표 60초, 소식 30초. |
| 버전 | 경로에 버전(`/api/v1/...`). 깨지는 변경은 `/api/v2`로 새로 열고 v1을 일정 기간 함께 둡니다. |
| 신원 | 지금은 익명 플레이어(기기에서 처음 한 번 만들고 토큰 보관). 나중에 구글 플레이 게임즈·스팀 계정을 같은 플레이어에 연결. |
| 안전한 배포 | D1 바인딩(`DB`)이 없으면 v1은 모두 `503 not_configured`를 돌려주고, 게임은 지금의 KV 래더를 그대로 씁니다. 그래서 DB를 만들기 전에 이 코드를 배포해도 아무것도 바뀌지 않습니다. |

## 2. 저장소 선택

### 왜 D1인가

래더 기능(2주 시즌, 단계별 상위 20명, 최근 승격 소식, 다른 유저 덱과의 맞대결 기록, 라이벌)은 "정렬해서 위에서 20개", "이 사람과 저 사람의 누적 기록" 같은 질의가 핵심입니다. KV는 키 하나를 읽고 쓰는 저장소라 정렬·집계를 하려면 목록 전체를 훑어야 합니다(지금 `/api/ladder/opp`가 그 단계 덱 전부를 `list`합니다). 사용자가 늘면 읽기 수와 지연이 그대로 늘어납니다.

D1은 SQLite라서 색인으로 위 질의를 몇십 줄 읽기로 끝냅니다. 무료 플랜에서도 쓸 수 있고, 같은 Worker에 바인딩 하나만 추가하면 됩니다.

### 한도와 가격 (2026-11-17 Cloudflare 문서 확인)

| 항목 | 무료(Workers Free) | 유료(Workers Paid, 월 $5) |
|---|---|---|
| Worker 요청 | 하루 10만 | 월 1,000만 포함, 이후 100만당 $0.30 |
| Worker CPU | 요청당 10ms | 월 3,000만 CPU-ms 포함, 이후 100만 ms당 $0.02 |
| D1 읽은 줄 | 하루 500만 | 월 250억 포함, 이후 100만당 $0.001 |
| D1 쓴 줄 | 하루 10만 | 월 5,000만 포함, 이후 100만당 $1.00 |
| D1 저장 | 총 5GB | 5GB 포함, 이후 GB-월 $0.75 |
| KV 읽기 / 쓰기 | 하루 10만 / 1,000 | 월 1,000만 / 100만 포함 |
| 정적 파일(사이트) | 무료·무제한 | 무료·무제한 |
| Cron Trigger | 따로 요금 없음(요청·CPU로 계산) | 같음 |
| D1 Time Travel(되돌리기) | 7일 | 30일 |

- **색인도 쓴 줄로 셉니다.** 색인이 걸린 열을 바꾸면 표 1줄 + 색인 1줄로 계산됩니다(문서 명시). 아래 비용 추정에 반영했습니다.
- Workers Rate Limiting 바인딩이 무료 플랜에서 되는지는 문서에 명시가 없어 **불확실**합니다. 그래서 코드는 바인딩이 없으면 메모리 기반 제한으로 동작합니다.

### KV는 그대로

- 기기 옮기기(최대 8MB 저장 덩어리, 7일 뒤 삭제)와 프런트컵(신청 덱·결과 JSON)은 KV가 더 맞습니다. 옮기지 않습니다.
- 래더 덱 본문(약 8KB)은 v1에서 D1 `decks.body`(TEXT)에 둡니다. 10만 명이어도 약 0.8GB라 5GB 안입니다. 나중에 커지면 본문만 KV나 R2로 옮기고 D1에는 해시만 두면 됩니다(`decks.h`가 이미 있습니다).
- 프런트컵 표를 D1에 복제하는 일은 이번에 하지 않았습니다(필요할 때 `cup_entries`, `cup_results` 표 추가).

## 3. API (`/api/v1`)

로그인: `Authorization: Bearer ft1.<32자>`(처음 `POST /player`가 한 번 줍니다). 관리자: `Authorization: Bearer <CUP_ADMIN>`(프런트컵과 같은 비밀값).

| 메서드·경로 | 설명 |
|---|---|
| `GET /health` | `{ok, schema, season}`. DB 없음 → 503 `not_configured`, 표 없음 → 503 `schema_missing` |
| `POST /player` | 토큰 없이: 새 익명 플레이어 `{nickname, platform}` → 201 `{player, token}`. 토큰과 함께: 닉네임(하루 1번)·플랫폼 바꾸기 |
| `GET /player/me` · `DELETE /player` | 내 정보 · **내 기록 전부 지우기**(플레이스토어의 계정 삭제 요구 대응) |
| `POST /player/link` · `POST /player/login` | 스팀·구글 플레이 게임즈 계정 연결 / 새 기기에서 같은 플레이어로 로그인. 비밀값이 없으면 501 |
| `PUT /ladder/deck` | 덱 등록·덮어쓰기 `{e, tier?, wid?}`. `tier`는 이 플레이어의 **첫 등록 때만**(예전 KV 래더 단계를 옮겨 올 때) 씁니다 |
| `GET /ladder/opponents?tier=&ovr=&n=9` | 같은 단계에서 OVR이 가까운 덱. 색인 범위 읽기 두 번(읽는 줄 ≈ 2n). 나·숨김·45일 넘게 안 고친 덱 제외 |
| `POST /ladder/result` | 리그 요약 `{key, rank, teams, w, l, d, opps:[{pid, w, l, d}]}` → 포인트·단계(공용 규칙 `ulTierAfter`)·맞대결·소식. 같은 `key`는 한 번만 셉니다 |
| `GET /ladder/leaderboard?tier=&season=` | 단계별 상위 20명(포인트 순). 60초 캐시 |
| `GET /ladder/feed` | 최근 승격·레전드 우승·시즌 상위 30건. 30초 캐시 |
| `GET /ladder/me` · `/ladder/rivals` · `/ladder/h2h/PID` | 내 시즌 기록·단계 안 순위·지난 시즌 칭호·최근 리그 / 라이벌(공격·수비) / 특정 유저와의 기록 |
| 관리자 `GET admin/stats` | 래더 현황(아래 7절) |
| 관리자 `GET admin/players?q=` · `PUT admin/hide` · `DELETE admin/player/PID` · `DELETE admin/deck/PID` | 찾기·숨김·삭제 |
| 관리자 `POST admin/season/roll` · `POST admin/migrate` | 지금 시즌 끊기 · 표 만들기(같은 SQL, 여러 번 해도 안전) |

포인트: 10팀 리그 순위별 `30, 24, 19, 15, 12, 9, 7, 5, 3, 1`(팀 수가 다르면 같은 비율 자리). 음수가 없어 많이 할수록 오릅니다. 순위표는 **지금 단계** 안에서 포인트 순입니다.

## 4. 표 (migrations/0001_init.sql)

| 표 | 내용 |
|---|---|
| `players(id, nickname, platform, created, last_seen, nick_at, hidden, wid)` | 플레이어. `id`는 `p`+16자. `wid`는 예전 세계 id(옮겨 오기용) |
| `devices(secret_hash, player_id, platform, created, last_seen)` | 기기 토큰의 SHA-256. 플레이어 하나에 기기 여러 개 |
| `identities(provider, provider_uid, player_id, created)` | 외부 계정(`steam`, `gpgs`). (provider, uid)는 한 플레이어에만 |
| `decks(player_id, name, year, ovr, ovr_json, tier, h, body, bytes, created, at)` | 플레이어당 현재 덱 하나. 색인 `(tier, ovr)` |
| `ladder_seasons(id, starts, ends, status, closed_at)` | 시즌 |
| `ladder_entries(season, player_id, tier, start_tier, best_tier, points, leagues, wins, ups, downs, titles, updated)` | 시즌별 내 칸. 색인 `(season, tier, points)` |
| `league_results(…, lkey, tier, to_tier, rank, teams, w, l, d, delta, opps, at)` | 리그 요약. `UNIQUE(player_id, lkey)`로 중복 방지. 180일 보관 |
| `h2h(player_id, opp_id, n, w, l, d, at)` | 내가 그 유저 덱을 상대한 누적 기록(방향 있음). 수비 기록은 반대 방향 줄을 뒤집어 보여 줍니다 |
| `events(season, kind, player_id, nickname, tier_from, tier_to, info, at)` | 소식(`promo`, `demote`, `crown`, `season_top`). 60일 보관 |
| `daily_stats(day, k, v)` | 하루 단위 집계(한국시간 날짜). 400일 보관 |
| `meta(k, v)` | 스키마 버전 |

## 5. 시즌

- 14일. 첫 시즌은 2026-11-16(월) 00:00 KST 기준 14일 칸에 맞춥니다.
- **게으른 교체**: 요청이 들어왔을 때 현재 시즌이 끝났으면 그 자리에서 닫고(단계별 1~3위에게 칭호, 소식 `season_top`) 다음 시즌을 엽니다. 두 요청이 동시에 와도 `UPDATE … WHERE status='open'`의 변경 수로 한 번만 시상합니다. 오래 비어 있었으면 지금이 속한 14일 칸으로 건너뜁니다.
- 새 시즌 단계: 그 플레이어가 새 시즌에 처음 덱을 올리거나 결과를 낼 때 **지난 시즌 단계 - 1**(루키는 그대로), 포인트 0. 시즌이 바뀔 때 모든 플레이어를 한꺼번에 옮기지 않아 쓰기 비용이 활동한 사람 수만큼만 듭니다.
- Cron Trigger(선택, 무료): `wrangler.jsonc`의 주석 `"triggers"`를 풀면 매일 한 번 같은 확인을 합니다. 없어도 됩니다.
- 관리자는 `POST /api/v1/admin/season/roll`로 지금 끊을 수 있습니다(새 시즌은 지금부터 14일).

## 6. 신원과 플랫폼(웹·안드로이드·스팀)

하나의 플레이어(`players`)에 여러 기기(`devices`)와 여러 외부 계정(`identities`)이 붙습니다.

1. **지금(웹)**: 처음 래더를 쓸 때 `POST /player`로 익명 플레이어를 만들고 토큰을 기기(localStorage)에 둡니다. 개인정보 없이 닉네임만 받습니다.
2. **안드로이드**: 두 가지 포장 중 하나.
   - **TWA(Trusted Web Activity)**: 지금 사이트를 그대로 띄웁니다. 같은 출처라 CORS 설정이 필요 없습니다. 가장 간단합니다.
   - **Capacitor**: 앱 안에 파일을 넣습니다. 출처가 `https://localhost`가 되므로 Worker 변수 `V1_ORIGINS`에 넣고, 연결부(`src/core/net.mjs`)의 `base`를 배포 주소로 정합니다.
   - 계정: 구글 플레이 게임즈 서비스 v2의 `requestServerSideAccess`로 받은 **server auth code**를 `POST /player/link {provider:'gpgs', code}`로 보내면, 서버가 `oauth2.googleapis.com/token`에서 교환하고 `games/v1/players/me`의 `playerId`를 확인합니다. 비밀값 `GPGS_CLIENT_SECRET`, 변수 `GPGS_CLIENT_ID`(웹 애플리케이션 OAuth 클라이언트). 정확한 PGS v2 서버 흐름은 앱 작업 때 구글 문서로 다시 확인합니다(**확인 필요**).
3. **스팀**: Electron 또는 Tauri로 포장. 출처는 Tauri가 `tauri://localhost`/`http://tauri.localhost`, Electron은 사이트를 원격으로 띄우면 같은 출처, 파일로 띄우면 `base` 지정.
   - 계정: Steamworks `GetAuthTicketForWebApi("fronttime")`로 받은 티켓(16진수)을 `POST /player/link {provider:'steam', ticket}`으로 보내면 서버가 `ISteamUserAuth/AuthenticateUserTicket`(partner.steam-api.com, 퍼블리셔 키)으로 확인해 `steamid`를 얻습니다. 비밀값 `STEAM_WEB_API_KEY`, 변수 `STEAM_APP_ID`. VAC·퍼블리셔 차단 계정은 거절합니다.
4. **다른 기기로 옮기기**: 새 기기에서 `POST /player/login {provider, ticket|code}` → 같은 플레이어의 새 기기 토큰. 웹끼리는 지금처럼 기기 옮기기(저장 코드)로 토큰도 함께 옮기는 방식을 다음 단계에서 붙입니다.

## 7. 관리자 '래더 현황'

설정 › 정보 › 관리자 → 관리자 페이지 위쪽 탭 **래더 현황**(`src/ui/cup/03_ladder_admin.js`). 한 번의 `GET /api/v1/admin/stats`로 다음을 보여 줍니다.

- 오늘/7일/30일: 활성 플레이어(겹치지 않게 센 수), 새 덱, 완료한 리그, 승격·강등
- 최근 14일 막대(완료 리그, 활성), 시간대별 리그 완료(7일 합, 한국시간)
- 단계별 분포(이번 시즌 참여 플레이어·등록 덱·리그 수)
- 플랫폼 비율(web/android/steam, 지금은 웹만)
- 상위 플레이어, 최근 소식, 최근 등록 덱 20개(숨기기·삭제 버튼)
- 오늘 서버 사용량 추정(D1 읽기·쓰기, KV 쓰기)과 무료 한도 대비 %

집계는 쓰기 요청 때 `daily_stats`에 몇 줄 더하는 방식(롤업)이라 화면을 열 때 읽는 줄이 적습니다. 사용량은 D1 응답의 `meta.rows_read/rows_written`과 KV 쓰기 횟수를 서버 인스턴스 메모리에 모았다가 다음 쓰기 때 더한 **추정치**입니다(정확한 값은 Cloudflare 대시보드 › D1 › 측정항목). D1이 없으면 지금의 KV 래더 기준으로 등록 덱 수·단계별 분포만 보여 주고 "D1을 연결하면 더 자세히" 안내를 띄웁니다.

## 8. 남용 방지·운영

| 항목 | 방법 |
|---|---|
| 요청 수 제한 | IP당 시간당 새 플레이어 10명, 플레이어당 10분에 쓰기 60번·읽기 240번. `V1_RL` 바인딩(Workers Rate Limiting)이 있으면 그것을 먼저, 없으면 서버 메모리로 대략 셉니다. DB·KV에 쓰지 않습니다. |
| 다른 사이트 | 쓰기 요청은 같은 출처 + `V1_ORIGINS`만. 로그인은 쿠키가 아니라 토큰이라 다른 사이트가 남의 이름으로 요청할 수 없습니다. |
| 크기 | 본문 120KB, 덱 40KB, 결과 16KB 이하. |
| 이름 | 닉네임·팀명은 프런트컵과 같은 금칙어·정리 규칙(`cupBadName`, `cupName`). 닉네임은 하루 한 번만 바꿉니다. |
| 숨김 | 관리자 숨김 → 순위표·소식·상대 목록·라이벌에서 빠집니다(기록은 남김). |
| 결과 조작 | 리그는 유저 기기에서 돕니다. 지금 래더 원칙대로 조작은 막지 않습니다. 같은 리그 두 번 제출만 막고, 이상치는 관리자 화면에서 보고 숨깁니다. |

## 9. 개인정보·보관

- 받는 것: 닉네임, 플랫폼(web/android/steam), 덱, 리그 요약. 이메일·실명·IP를 저장하지 않습니다(IP는 요청 제한용 해시를 메모리에만 잠깐).
- 외부 계정을 연결하면 그 계정 id(steamid, Play Games playerId)만 둡니다.
- 지우기: 본인 `DELETE /api/v1/player`(앱 스토어 계정 삭제 요구), 관리자 `DELETE /api/v1/admin/player/PID`. 다른 사람의 맞대결 기록에 남은 줄도 함께 지웁니다.
- 보관: 리그 결과 180일, 소식 60일, 일별 집계 400일(시즌을 바꿀 때 지웁니다). `docs/privacy.md`에 이 항목을 추가해야 합니다(서버를 켤 때).

## 10. 백업

- D1 **Time Travel**은 항상 켜져 있습니다(무료 7일, 유료 30일). `npx wrangler d1 time-travel restore fronttime-db --timestamp=<유닉스 시각>`으로 그 시점으로 되돌립니다(되돌리기도 북마크가 남아 다시 되돌릴 수 있습니다).
- 장기 보관이 필요하면 `npx wrangler d1 export fronttime-db --remote --output=backup.sql`를 시즌마다 받아 둡니다.

## 12. 화면 연결 순서(래더 화면이 v1로 옮겨 가는 법)

지금 래더 화면(`src/ui/uladder/01_uladder_ui.js`, 래더 재미 작업 중인 화면)은 그대로 `/api/ladder`(KV)를 씁니다. 래더 재미 작업이 합쳐진 뒤 다음 순서로 옮깁니다.

1. 연결부 만들기: `const NET = FrontOfficeCore.netCreate({})`. 처음 `NET.probe()` → `'ok'`이면 v1, `'off'`(503 not_configured)면 지금 KV 길을 그대로 씁니다. 처음에는 숨은 스위치(`FrontOfficeCore.netEnabled()`: localStorage `fo-net-v1`=`1` 또는 주소 `?net=v1`)가 켜진 경우에만 v1을 씁니다.
2. 플레이어: 래더를 처음 열 때 `NET.ensurePlayer(닉네임, {wid: cupWid()})`. 닉네임은 단장 이름 또는 직접 입력.
3. 덱 등록: `ulUpload`에서 `NET.putDeck(U.deck.e, U.tier, cupWid())`. 첫 등록 때 지금 단계를 옮겨 옵니다.
4. 상대: 리그 시작 때 `NET.opponents({n: 9})` → `decks[].e`, 상대마다 `pid`·`nickname`을 리그 팀에 붙여 둡니다.
5. 리그가 끝나면: `NET.result({key: 리그 id, rank, teams, w, l, d, opps: [{pid, w, l, d}]})` → 응답의 `tier`를 내 단계로 씁니다(서버가 계산). 연결이 끊기면 연결부가 줄 세웠다가 다음에 보냅니다.
6. 새 화면 조각: 순위표 `NET.leaderboard(tier)`, 소식 `NET.feed()`, 내 시즌·칭호 `NET.me()`, 라이벌 `NET.rivals()`, 특정 상대 `NET.h2h(pid)`.
7. 충분히 확인되면 숨은 스위치를 기본으로 켜고, 일정 기간 뒤 `/api/ladder`(KV)를 읽기 전용으로 남겼다가 정리합니다.
